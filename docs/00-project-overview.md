## 2. 项目基本信息

### 2.1 项目身份

- 公司名称：**医数云策科技有限公司**
- 产品名称：**医数云策——智慧医疗运营大数据与 AI 决策分析平台**
- 团队规模：5 人
- 数据基础：约 200 万条住院出院记录；当前轻量摸数依据为 2021 年纽约州 SPARCS 住院出院数据样本

### 2.2 一句话定位

面向医院运营管理与医疗数据分析人员，对住院数据进行清洗、存储、统计和可视化，并通过受控的 AI 问数能力辅助用户理解医院、疾病、患者群体及费用成本情况。

### 2.3 核心价值

1. 将大规模住院数据加工为口径统一、可以复查的分析结果。
2. 用图表帮助用户快速发现医院运营、疾病结构和费用成本特征。
3. 用自然语言降低查询门槛，但所有 AI 数值答案必须来自系统分析接口。
4. 用一条可运行、可测试、可演示的完整链路体现课程所学技术。

## 3. 目标用户与核心问题

### 3.1 目标用户

| 用户 | 主要需求 |
|---|---|
| 医院运营管理人员 | 查看整体业务规模、住院效率、急诊占比、费用与成本情况 |
| 医疗数据分析人员 | 按医院、疾病、年龄、性别、严重程度等维度进行统计分析 |
| 科室或业务管理人员 | 了解重点疾病、患者群体和高费用群体的结构特征 |
| 项目演示与教学评审人员 | 验证数据处理、大数据分析、后端、前端和 AI 链路是否真实打通 |

### 3.2 要解决的核心问题

- 大规模住院数据如何形成可信、统一的统计口径；
- 哪些医院和疾病的病例量、住院时长、费用或成本较突出；
- 不同患者群体、严重程度和支付方式之间存在怎样的统计差异；
- 用户如何通过页面筛选或自然语言快速获得可追溯的分析结果。

### 3.3 产品边界

本产品是**医疗运营与数据分析平台**，不是医疗诊断系统。

- 一行数据代表一次住院出院记录，不代表一个唯一患者；
- 只做群体统计和运营分析，不提供个人诊断、处方或治疗建议；
- 不根据当前单年观察数据输出因果结论；
- 不承诺患者再入院追踪或连续病程分析，因为数据没有患者唯一 ID；
- AI 只负责识别查询意图、调用白名单分析工具和解释结果，不直接计算全量原始数据。

## 4. 候选功能全集

### 4.1 使用规则

候选功能分为四种建议优先级：

| 标识 | 含义 |
|---|---|
| MVP | 第一条最小完整闭环，优先验证技术链路 |
| 核心 | MVP 稳定后优先实现，构成可演示业务版本 |
| 增强 | 核心版本稳定且时间允许时实现 |
| 储备 | 当前只保留设计，不纳入本轮主要开发计划 |

### 4.2 数据接入、治理与管理

| 候选功能 | 说明 | 建议优先级 |
|---|---|---|
| 原始 CSV 接入 | 将规定数据放入统一输入目录或 HDFS 原始层 | MVP |

## 5. 第一轮 MVP 功能

### 5.1 MVP 唯一目标

第一轮只完成一个可验证的最小完整闭环：

> **疾病病例量 TOP10：从真实数据到 ECharts 图表完整跑通。**

MVP 的目的不是一次做出完整产品，而是证明五个岗位的成果能够按同一套字段、数据、接口和验收标准连接起来。

### 5.2 MVP 包含的功能

1. 读取一份真实 CSV 样例。
2. 清洗并标准化 CCSR 主诊断描述等本功能所需字段。
3. 使用 Spark Job 或 Hive SQL 聚合疾病病例量 TOP10。
4. 将结果放入后端可稳定查询的位置。
5. 提供一个 Flask GET API，例如 `GET /api/diseases/top?limit=10`。
6. Vue 页面请求真实 API，并用 ECharts 横向柱状图展示结果。
7. 页面具备加载、正常、空数据和错误四种状态。
8. 使用独立 SQL 或脚本核对 TOP10 名称、排序和病例数。
9. 记录运行方式、数据来源、接口示例和验收结果。

### 5.3 MVP 暂不包含

- 完整运营驾驶舱；
- 医院、患者群体和费用成本的完整页面；
- AI 问数；
- 机器学习模型；
- 登录、角色权限和后台管理；
- 多条件复杂联动筛选；
- 数据导出、报表生成和炫酷大屏；
- 多轮对话、Redis、本地大模型或复杂调度平台。

### 5.4 MVP 完成标准

- [ ] 页面数据来自真实后端接口，不是前端写死或未标识的 Mock 数据；
- [ ] 聚合任务可以重复执行并得到一致结果；
- [ ] API 的字段、类型和错误响应已有文档；
- [ ] 图表能正确显示名称、数量、排序和单位；
- [ ] 正常、加载、空数据和错误状态均已验证；
- [ ] 结果已通过独立 SQL 或脚本核对；
- [ ] 在组长电脑上按文档能够重新运行；
- [ ] 代码、测试证据和必要文档已进入 Git。

## 6. 分阶段实现目标

> 阶段编号沿用现有开发规范。每一阶段通过门禁后，再把主要精力投入下一阶段。

### 6.1 当前：先启阶段——范围确认

目标：只把产品边界、候选功能、MVP 和阶段顺序确定下来，不进入大规模编码。

主要产出：

- `docs/00-project-overview.md`；
- 后续的数据字典、数据可行性、需求、产品地图、指标和算法方案的编写任务；
- 全组确认的一期范围与暂不实现清单。

放行条件：

- [ ] 五名成员已阅读本文；
- [ ] 对产品定位、目标用户和非目标没有明显分歧；
- [ ] 同意第一轮只做疾病病例量 TOP10；
- [ ] 候选功能不被误解为全部必须实现；
- [ ] 老师的硬性技术要求已复核。

### 6.2 M0：工程基线

目标：所有人拥有一致、可启动、可协作的基础工程。

本阶段实现：

- 仓库目录、开发分支、PR 和 Commit 规则；
- Python、Node.js、Hadoop、Spark、Hive、MySQL 等环境版本表；
- 后端、前端、数据和 AI 模块的最小工程骨架；
- `.env.example`、端口、启动顺序、日志和健康检查约定；
- MVP 数据流、表结构草案和 API 契约。

暂不实现：任何完整业务页面、AI 和算法模型。

通过条件：五名成员都能拉取项目并完成自己模块的基础启动。

### 6.3 M1：最小闭环

目标：完成“疾病病例量 TOP10”真实全链路，即本文第 5 节 MVP。

本阶段实现：

- 一份真实数据；
- 一组必要清洗规则；
- 一个可重复执行的聚合任务；
- 一个正式 API；
- 一个包含四态的图表；
- 一份独立核对结果。

暂不实现：第二个业务模块、AI、算法、复杂筛选和页面美化。

通过条件：数据可追溯、接口可访问、页面可展示、结果可核对，并能在组长环境重新运行。

### 6.4 M2：核心分析版本

目标：在不破坏 MVP 的前提下，形成可完整演示的医疗运营分析产品。

按以下顺序逐步实现：

1. 疾病洞察核心指标；
2. 运营驾驶舱核心 KPI；
3. 医疗机构核心分析；
4. 费用与成本核心分析；
5. 患者群体基础分析；
6. 公共筛选、指标口径和页面四态。

M2 建议控制为 4—5 个核心页面，不要求把第 4 节所有功能全部实现。增强型详情、复杂联动和导出功能视进度决定。

通过条件：驾驶舱、医院、疾病和费用核心指标可稳定使用；P0/P1 接口进入冻结；核心页面无阻塞错误。

### 6.5 M3：AI 与算法增强

目标：核心业务系统稳定后，再增加项目特色能力。

优先实现：

- 至少 3 类单轮受控问数；
- 白名单 Tool 调用已有分析 API；
- 回显查询条件、数据来源和指标口径；
- 返回结构化数据、图表和文字解释；
- 超出能力范围时明确拒答。

可选实现：

- 高费用病例分类或费用等级预测二选一；
- 模型评估面板；
- 少量有业务价值的增强图表。

本阶段仍不优先实现多轮对话、自由 SQL、本地大模型和复杂模型集成。

通过条件：AI 至少稳定支持 3 类问题，所有数字均来自白名单 Tool；如实现算法，必须有无泄漏的特征说明和可复查评估结果。

### 6.6 M4：测试、产品化与交付

目标：把“能运行”整理成“能部署、能演示、能答辩、能回退”。

本阶段实现：

- 功能、接口、数据、AI 和端到端测试；
- 错误处理、日志、配置和敏感信息检查；
- 干净环境重新部署；
- README、部署说明、用户手册和测试记录；
- 演示数据、答辩路线、稳定 Git Tag 和回滚版本；
- 只在不影响稳定性的情况下进行必要的视觉优化。

通过条件：按照文档可在组长电脑重新部署，并完整演示核心业务链路和 AI 增强链路。

## 8. 技术链路与硬约束

当前材料确定的总体链路为：

```text
原始医疗 CSV
  → HDFS
  → Pandas / Spark 清洗与分析
  → Hive
  → MySQL 服务结果
  → Flask REST API
  → Vue + ECharts
  → 用户查看分析结果
```

AI 增强链路为：

```text
用户问题
  → LangChain Agent
  → 白名单分析 Tool / Flask API
  → 真实结构化结果
  → 大模型生成解释
  → 文字 + 图表
```

必须遵守：

1. 核心展示数据必须来自真实处理链路，不能用写死数据冒充完成。
2. 数据字段、指标、表结构和 API 必须有统一口径。
3. AI 不直接计算约 200 万条原始数据，不直接执行任意 SQL。
4. 收费与成本必须分开表达；金额、比例和住院天数必须标明单位。
5. 费用和住院时长明显右偏，核心页面应同时考虑中位数或分位数。
6. 原始数据、密钥、数据库密码和个人绝对路径不得提交到仓库。
7. 具体软件版本、Hive/MySQL 边界和 AI Provider 在相应阶段确认，不在本文中提前写死。

## 9. 范围调整原则

当进度不足时，按以下顺序保留功能：

```text
完整可运行闭环
  > 核心业务功能
  > AI 项目特色
  > 算法与高级增强
  > 视觉特效和非必要平台能力
```

新增功能必须回答：用户为什么需要、使用哪些字段、计算什么指标、有哪些筛选条件、如何展示、与其他功能如何连接。回答不清楚的功能先留在候选池，不进入开发。

任何范围变化都应同步更新本文和相关需求、产品地图、指标、API 与任务文档。
