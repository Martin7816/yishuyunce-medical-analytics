## 1. 我们要做什么

**医数云策**是一套智慧医疗运营大数据与 AI 决策分析平台。

当前数据基础是老师提供的 2021 年纽约州 SPARCS 住院出院数据，共 **2,101,588 条数据记录**。我们计划围绕医院、疾病、住院记录群体、住院时长、医疗费用和成本进行统计分析，并通过网页图表和受控 AI 问数展示结果。

产品主要面向医院运营管理人员和医疗数据分析人员，帮助他们更快看懂医疗数据。

本项目只做医疗运营和群体数据分析，**不提供个人诊断、处方或治疗建议**。

需要统一理解：数据中的一行代表一次住院出院记录，不等于一个唯一患者。当前数据没有患者唯一 ID，因此不做患者跨次住院追踪，也不输出个人层面的医疗判断。

## 2. 系统准备怎么做

```text
医疗 CSV 原始数据
  → HDFS 保存原始数据
  → Pandas / Spark 完成清洗与聚合
  → Hive 保存和查询分析数据
  → MySQL 保存后端需要的服务结果
  → Flask 提供 API
  → Vue + ECharts 展示图表
  → LangChain + 大模型实现 AI 问数
```

AI 不直接计算原始数据，而是调用我们已经验证过的分析 API，再对真实结果进行解释。

以上是第2组当前采用的最小候选链路。老师样例和课程方向只提供参考，具体组件按能运行、能核对、能展示的原则自主确定；后续如出现学校明确要求，再在不破坏 M1 的前提下补入对应环节。不为了凑技术数量增加无用模块。

## 3. 候选功能

下面是完整的候选方向，但**不代表本次要一次全部完成**。

- 运营驾驶舱：病例数、医院数、平均住院时长、平均费用、平均成本、急诊比例。
- 医院分析：医院病例量、主要疾病、住院时长、费用成本和医院对比。
- 疾病分析：疾病排行、住院记录群体结构、住院情况、费用、严重程度和疾病画像。
- 住院记录群体分析：按年龄、性别、医院、疾病、入院方式和严重程度进行筛选。
- 费用成本分析：费用分布、成本差异、住院时长关系和高费用群体。
- 智能算法：高费用病例分类或费用等级预测，是否实现要等核心功能稳定后再决定。
- AI 数据助手：用自然语言查询疾病、医院、住院记录群体和费用指标。
- 数据管理：数据清洗、质量检查、分析任务和结果更新。

## 4. 第一轮 MVP

第一轮只完成一个功能：

> **疾病病例量 TOP10**

这里的“病例量”统一指住院出院记录数：以主诊断描述分组，每条有效住院出院记录计数一次。缺失值处理、并列排序等细节在指标文档中确认。

需要跑通完整链路：

```text
真实数据
  → 清洗疾病字段
  → Spark / Hive 统计 TOP10
  → MySQL 服务结果
  → Flask API
  → Vue 请求接口
  → ECharts 柱状图
  → 独立核对结果
```

完成标准：

- [ ] 使用真实数据，不用前端写死数据冒充结果；
- [ ] 清洗与聚合任务可以重复执行并得到一致结果；
- [ ] Flask API 可以访问，并有明确的字段和错误响应；
- [ ] ECharts 图表正确展示名称、数量、排序和单位；
- [ ] 页面具备加载、正常、空数据和错误四种状态；
- [ ] TOP10 已使用独立脚本或 SQL 核对；
- [ ] 能按照文档在组长电脑上重新运行；
- [ ] 代码、测试证据和必要文档已经进入 Git。

在这个闭环完成前，不同时开发大量页面、AI 或机器学习功能。

## 5. 分阶段实现目标

| 阶段 | 目标 |
|---|---|
| 当前：确定范围 | 确认项目定位、候选功能、MVP 和暂不实现内容 |
| M0：工程基线 | 建立目录、环境、Git 规则、数据流和接口约定 |
| M1：最小闭环 | 完成“疾病病例量 TOP10”全链路 |
| M2：核心分析 | 逐步完成疾病、驾驶舱、医院、费用和住院记录群体核心页面 |
| M3：必要扩展 | M1/M2 稳定后，结合课程交付需要和数据可支持程度补充一个可解释的分类模型；受控 AI 问数仅在时间允许且不影响主链路时加入 |
| M4：测试交付 | 完成测试、部署、使用说明、演示版本和答辩材料 |

每个阶段通过验收后再进入下一阶段。新增功能不能破坏已经跑通的版本。

## 6. 当前不优先做什么

- 不做个人诊断、治疗建议和患者连续病程追踪。
- 不做多轮 AI、自由 SQL、本地大模型和复杂权限。
- 不做微服务、Kubernetes、复杂调度平台和大型后台系统。
- 不为了好看堆砌 3D 图表、动画和重复页面。
- M2 核心分析稳定前，不把机器学习作为主任务。

## 8. 全组共同原则

1. 先确定需求和接口，再写代码。
2. 先跑通一条完整链路，再增加功能。
3. 功能必须使用真实数据，并且能够核对。
4. 每个任务都要有负责人、输入、输出和验收标准。
5. 遇到数据、接口、环境或依赖问题要及时说明。
6. 代码、测试和文档一起提交，保持项目随时可以运行。
7. 原始完整数据、密码、API Key、`.env` 和个人绝对路径不得提交到 Git。
8. 字段、指标、表结构、API 或公共环境发生变化时，必须先通知上下游成员。
