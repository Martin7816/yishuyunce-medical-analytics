# 医数云策小组开发规范

## 1. 共同目标

五名成员在同一仓库交付一套可运行、可核对、可展示的住院运营分析系统。业务术语以 `CONTEXT.md` 为准，产品范围以 `docs/00-project-overview.md` 为准，公共数据结构以 `docs/07-terminal-product-contract.md` 为准，任务与证据以 GitHub Issue 为准。

开发遵守以下原则：

1. 一项业务事实只维护一份权威定义；
2. 数据、API 和页面围绕同一条纵向链路协作；
3. 技术和目录只为明确问题服务；
4. 作者验证自己的交付，质量负责人独立复核关键结果；
5. 联调快照与真实数据结论始终分开；
6. 密钥、凭证、完整 CSV 和大型工件不进入 Git。

## 2. 目录职责

```text
backend/      Flask 应用、数据读取、业务校验和接口测试
frontend/     Vue 页面、ECharts 组件和前端构建
data/        PySpark 任务、SQL、固定样例和数据测试
 shared/      数据发布与读取共同使用的结构校验
 docs/        产品、架构、运行、接口和验收说明
 evidence/    Issue 执行证据和交接记录
 CONTEXT.md   业务术语
 README.md    项目入口和启动流程
```

目录按功能边界组织，不按成员划分私人区域。没有实际代码或交付物时不创建空目录。

## 3. 公共事实

| 事实 | 权威位置 |
|---|---|
| 业务术语 | `CONTEXT.md` |

同一事实不得在多个文件中维护不同定义。其他文档引用权威位置，并只补充自己的用途。

## 4. 任务流程

1. 在 GitHub Issue 中写明问题、范围、不做内容、负责人、输入、输出和验收矩阵；
2. 从最新 `main` 创建任务分支；
3. 先确认上游契约和可使用的固定样例；
4. 实现任务范围内的代码、测试和文档；
5. 执行与改动相关的自动化和真实环境检查；
6. 检查差异中没有密钥、工件或无关文件；
7. 创建 PR，写明验证命令、实际结果、已知限制和下游交接；
8. Review 通过后合并；
9. 在 Issue 中发布 Resolution 和证据入口。

详细操作见 `Issue任务领取与完成说明_V1.0.md` 与 `Git-Issue与个人修改提交全流程.md`。

## 5. 分支与提交

分支名称使用：

```text
feat/<issue>-<topic>
fix/<issue>-<topic>
docs/<issue>-<topic>
test/<issue>-<topic>
```

提交信息使用：

```text
feat(scope)(#issue): summary
fix(scope)(#issue): summary
docs(scope)(#issue): summary
test(scope)(#issue): summary
```

一个提交只表达一个逻辑结果。不要把自动生成目录、虚拟环境、完整数据或无关格式化混入提交。

## 6. 公共变更

下列内容影响多个角色，必须通过 Issue、文档、代码和测试一起确认：

- 业务术语；
- 指标公式、单位、排序和空值规则；
- 数据表、快照字段和实体键；
- API 路径、参数、响应与错误码；
- 页面路由、筛选和状态语义；
- Python、Java、Node、MySQL 等环境基线；
- 模型特征与 AI 工具白名单。

发现冲突时先定位权威文档与实际代码，再决定哪一方需要对齐；不能在单个下游模块中形成局部规则。

## 7. 测试要求

### 数据任务

- 固定样例验证清洗、排序、空值和边界；
- 真实 CSV 记录文件指纹、行数、模块数和版本；
- 独立脚本不复用 PySpark 聚合实现；
- 发布器验证完整批次、幂等和事务回滚。

### 后端

- 正常、合法空结果和依赖失败；
- 未知、重复、非法参数和错误 HTTP 方法；
- 响应信封、追踪编号和敏感信息保护；
- Fixture 与 MySQL 读取遵守同一服务接口。

### 前端

- loading、success、empty、error、retry；
- 筛选白名单、请求竞态和清空行为；
- 指标、单位、顺序、版本与 API 一致；
- 桌面与移动端布局、控制台和可访问性。

### 模型与 AI

- 固定随机种子、特征白名单和泄漏字段拒绝；
- 回答来源、工具轨迹和数据版本可追踪；
- 密钥缺失、超时、错误和断网返回真实失败。

## 8. 完成标准

任务完成同时满足：

- 问题得到明确回答；
- 约定的代码、工件或文档存在；
- 测试和真实环境结果可复查；
- 公共文档与代码一致；
- PR 已合并到目标分支；
- 下游知道输入、配置、命令和限制；
- Issue 包含最终 Resolution。

PR 合并、代码能启动或口头确认都不能单独代表任务完成。

## 9. 安全要求

禁止提交：

- 完整 SPARCS CSV 和原始住院明细；
- `.env`、数据库密码、SSH 私钥和 API Key；
- 含真实连接信息的日志或截图；
- 完整快照、模型工件和虚拟环境；
- 无授权的个人医疗结论。

错误响应和日志使用稳定错误类型与追踪编号，不输出底层异常和敏感配置。

## 10. 交付节奏

截至 2026 年 8 月 20 日，七个运营分析模块具备真实链路证据；数据质量、高费用记录分类、AI 问答和最终集成属于交付收口范围。团队优先完成真实专项验收、干净仓库复现、文档、用户说明、答辩材料和彩排，不扩大产品实体或技术栈。
