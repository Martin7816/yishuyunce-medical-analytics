## 0. 文档定位

本规范说明第2组怎样围绕同一条数据链协作、怎样提交代码以及怎样判断任务完成。项目的逐步执行顺序以 `组长推进图001.md` 为准，项目范围以仓库 `docs/00-project-overview.md` 为准，业务术语以仓库根目录 `CONTEXT.md` 为准，任务和决策过程以 GitHub Issues（含 Wayfinder 地图）为准。本文件不再单独发明另一套推进顺序。

本规范遵循以下原则：

1. 先跑通一条真实、可核对、可演示的最小闭环，再增加功能；
2. 岗位表示质量责任，不表示个人独占目录；
3. 目录和文档按实际任务创建，不提前堆放空壳；
4. 一个事实只维护一份，避免任务板、指标和接口出现多个版本；
5. 老师样例只作参考，第2组按项目概况自主确定技术和功能，不把样例内容写成已经完成的事实；
6. 在满足验收、稳定性和展示效果的前提下，采用依赖更少、维护成本更低的方案。

### 1.1 “范围确认通过”是什么意思

范围确认通过不要求所有细节已经设计完成，但至少需要满足：

- 五名成员阅读项目概况，并明确回复同意或提出具体异议；
- 第一轮只完成“疾病病例量 TOP10”真实数据闭环；
- 明确第一轮不做复杂 AI、登录、微服务和大量附加页面；
- 明确五人的主责方向和最终以组长电脑可运行版本为准；
- 实际数据文件能够读取，MVP 所需字段有核验路径；
- 项目组已经明确不等待老师逐项指定技术，技术选择以可运行、可核对和可展示为准。

影响后续扩展的未决事项不阻塞数据侦察、固定样例、接口草案和 M1 开发；新增技术必须保持可替换，并说明其解决的具体问题。

### 3.1 配置与依赖的归属

- `backend/app/config.py` 属于后端 Python 代码，放在 `backend/app/`；它只负责读取环境变量并组织配置，不保存密码、Token 或 API Key。
- `backend/.env.example` 只描述后端运行所需的环境变量；真实的 `backend/.env` 仅存在于本地，并且必须写入 `.gitignore`。
- `backend/requirements.txt` 只维护后端 Python 运行和测试依赖。前端依赖继续由 `frontend/package.json` 管理；未来确实形成独立运行环境的数据或 AI 模块，再在对应模块维护自己的依赖文件。
- 根目录不再默认放后端的 `.env.example`、`.env` 或 `requirements.txt`。只有在全组确认整个仓库长期共用同一个 Python 环境时，才可以重新提议统一到根目录，并同步修改本规范、启动说明和验证脚本。
- 如果前端确实需要环境变量，使用 `frontend/.env.example` 单独描述；前端和后端不得共用含义不清的环境变量名。

以上内容是目录结构、配置归属和团队协作约定，不代表相应目录、配置文件或业务代码已经创建或完成；实际完成状态只以仓库内容、GitHub Issue、PR 和验收证据为准。

以下内容只在条件满足后创建：

- M1 稳定且数据具备可靠标签时，再创建数据侧的模型目录；
- M1 稳定且 AI 对展示确有价值时，再创建 `ai/` 或后端 AI 模块；
- 确实需要部署文件时再创建 `deploy/`；
- 不为短期项目预先创建 `integration/release/rollback`、复杂分层、空迁移目录或大量空 README。

## 5. 项目数据链

第一轮必须跑通的业务链路是：

```text
真实 CSV
  → 字段核验和清洗
  → 疾病病例量 TOP10 聚合
  → 可供后端读取的服务结果
  → Flask API
  → Vue + ECharts
  → 独立脚本或 SQL 核对
```

HDFS、Spark、Hive、MySQL 等具体技术如何进入链路，由第2组结合真实数据和组内环境在 `docs/03-architecture-and-env.md` 冻结。每个组件都必须有明确职责；确认使用时，建议边界为：

- HDFS：保存需要展示的大数据原始文件；
- Spark/Hive：执行清洗、聚合或保存分析结果，避免两处复制同一份规则；
- MySQL：保存 Flask 需要读取的小型服务结果，不重新计算指标；
- Flask：提供稳定 API，不在 Route 中堆放长 SQL；
- Vue/ECharts：只调用 API，不直连数据库或重新计算正式指标；
- 后续 AI：只调用已经验证的白名单 API，不读取完整原始数据或执行任意 SQL。

无论最终采用哪些组件，TOP10 的清洗、分组、排序和并列规则只能有一份正式定义。

## 6. 契约状态与公共变更

字段、指标、数据结果和 API 可使用三种状态：

- `DRAFT`：可以讨论和修改，不能作为下游稳定依据；
- `CONFIRMED`：相关上下游已经确认，可以并行开发；
- `FROZEN`：已经进入联调，原则上只修错误，不随意改变结构。

API 编码前，`docs/04-api.md` 至少写清：

```text
接口名称和负责人：
Method 和 URL：
请求参数、类型和范围：
正常返回字段、类型、单位和排序保证：
合法空结果：
非法参数和服务失败：
数据来源及对应指标：
状态：DRAFT / CONFIRMED / FROZEN
```

下列公共变更必须先创建或更新 GitHub Issue，通知所有受影响成员，再通过 PR 同时修改文档、代码和测试：

- 数据字段、类型、枚举、清洗和缺失值规则；
- 指标公式、单位、统计范围和排序规则；
- Hive/MySQL 表结构或服务结果字段；
- API 路径、参数、响应字段和错误语义；
- 公共依赖、环境变量名、环境版本、端口和启动顺序；
- 已确认的 M0/M1 范围。

## 7. Git 与 GitHub 协作

### 7.1 分支和流程

剩余工期较短，使用稳定 `main` 加短生命周期分支，不额外维护长期 `dev` 分支：

```text
main                                  随时可运行、可演示
feature/<issue-number>-<short-name>   功能或数据任务
fix/<issue-number>-<short-name>       缺陷修复
docs/<issue-number>-<short-name>      仅文档
```

正常流程：

```text
领取 GitHub Issue
  → 从最新 main 创建分支
  → 完成一个明确任务
  → 本地验证并同步文档
  → push 并创建 PR 到 main
  → 至少一名相关上下游 Review
  → 检查通过后合并
```

- 禁止把未经 Review 的日常开发直接推到 `main`；
- 一个分支只解决一个主要 Issue，预计超过两天的任务必须继续拆分；
- 公共契约变更必须邀请所有受影响的上下游成员 Review；
- 紧急修复也要保留 Issue、验证记录和 PR，不以“时间紧”为由失去可追踪性。

### 7.2 Commit

```text
<type>(<scope>): <简短说明>
```

`type` 使用 `feat`、`fix`、`docs`、`refactor`、`test`、`chore`；`scope` 推荐使用 `data`、`api`、`web`、`ai`、`quality`、`integration`。

### 7.3 PR 最低内容

- 关联的 Issue 和本次目标；
- 修改了哪些目录；
- 是否改变字段、指标、表、API 或公共环境；
- 实际执行的验证命令与结果；
- 页面附必要截图，API 附代表性请求/响应，数据任务附固定样例核对结果；
- 已知限制和需要下游继续处理的事项。

## 8. 测试与完成标准

第一轮采用少而关键的测试，不要求每个文件机械覆盖所有测试类型。

| 层级 | 最低验证 |
|---|---|
| 数据 | 固定小样本有期望结果；重复执行结果一致；空值和异常值处理符合指标文档 |
| API | 正常结果、合法空结果、非法参数和依赖失败；字段、类型、单位、排序符合契约 |
| 前端 | 加载、正常、空数据、错误四种状态；图表名称、数量、排名和单位正确 |
| 端到端 | 同一固定样例在数据结果、API 返回和前端展示中一致；独立脚本或 SQL 能核对 |
| 运行环境 | 按 README 在组长电脑重新启动，所需配置不依赖个人绝对路径和未记录操作 |

任务只有同时满足以下条件才是 `DONE`：

- 关联 Issue 的验收标准已经满足；
- 代码或文档进入正确目录，并能在目标环境实际运行；
- 作者完成本模块验证，相关上下游完成 Review；
- 字段、指标、API、环境等公共事实已经同步；
- PR 已合并到 `main`，下游成员能够使用；
- 没有提交密钥、完整原始数据、缓存、日志和无关文件；
- 有可复查的命令、响应、测试记录或必要截图；
- 未完成内容已另建 Issue，不使用“基本完成”代替。

## 9. 数据与文件安全

不得提交 Git：

- 完整 SPARCS 原始数据和可重新生成的大型中间结果；
- `.env`、密码、Token 和 API Key；
- 日志、缓存、虚拟环境、`node_modules/`、前端构建产物和模型大文件；
- 个人电脑绝对路径、临时测试文件和无关资料。

可以提交：

- 脱敏小样本及对应期望结果；
- `backend/.env.example` 等不含真实密钥的配置模板；
- 可重复执行的 Python、Spark、SQL、初始化和测试脚本；
- 小型测试摘要、必要截图和真实运行说明。

配置和依赖文件按模块归属维护：后端使用 `backend/.env.example`、本地 `backend/.env` 和 `backend/requirements.txt`；前端如有独立环境变量则使用 `frontend/.env.example`。真实 `.env` 文件一律不得提交。

根目录不得长期散落 `test.py`、`demo.sql`、`new.py`、`final_v2.py` 等临时文件。验证完成后移动到正确目录或删除。

## 11. 每日推进规则

建议每天保持一次短同步和一次集成检查：

1. 开工前：每人在 GitHub Issue 更新“今天做什么、依赖谁、是否被阻塞”；
2. 开发中：出现字段、接口、环境或进度阻塞时立即提出，不等到晚上汇报；
3. 当日集成：合并已经通过 Review 的小 PR，验证当前 `main` 仍能运行；
4. 收工前：更新 Issue 状态、验证证据和下一步，不创建含糊的“基本完成”；
5. 王敬博每天优先处理阻塞和公共契约，不替所有成员包办编码。

出现以下情况时，立即暂停新增功能并集中处理：

- 固定样例在不同模块得到不同结果；
- 公共字段或 API 被成员各自修改成不同版本；
- `main` 无法启动或组长电脑无法复现；
- M1 进度晚于 8 月 21 日目标；
- 新功能无法说明对应的课程交付要求、用户价值或验收作用。
