# 医数云策项目组员执行说明

## 1. 共同交付

全组在同一仓库完成一套可运行、可核对、可展示的住院运营分析系统。数据中的一行表示一次住院出院记录，“病例量”表示有效记录数，不表示患者人数。系统不提供个人诊断、处方、治疗建议或跨次住院追踪。

项目包含运营驾驶舱、医院、疾病、住院记录群体、费用成本、病情风险、支付和 AI 问答八个页面入口；数据质量校验与高费用记录分类保留为后端能力，不提供独立页面。

## 2. 进展位置

截至 2026 年 8 月 20 日：

- 运营驾驶舱、医院、疾病、住院记录群体、费用成本、病情风险和支付方式具备真实数据链路证据；
- 数据质量校验与高费用记录分类具备代码和 API；AI 问答具备代码、API 与页面入口；
- 工作重点是完成后三项真实环境专项验收、全仓回归、组长电脑复现、文档、答辩材料和彩排；
- 联调快照只能证明接口与页面行为，不代表真实分析结论。

## 3. 执行路线

```text
确认 Issue 与公共契约
        ↓
准备固定样例或真实输入
        ↓
实现任务范围内的代码、测试和文档
        ↓
执行自动化与目标环境验证
        ↓
记录证据并交给下游
        ↓
PR Review 与集成
        ↓
发布 Resolution 并关闭 Issue
```

## 4. 领取任务前

1. 阅读 Issue 的问题、范围、不做内容、负责人、输入、输出和验收矩阵；
2. 阅读与任务相关的公共文档；
3. 确认上游输入已经存在，或明确哪些工作可以用固定样例并行；
4. 从最新 `main` 创建独立分支；
5. 检查工作区中没有别人的未提交改动。

## 5. 开发中

- 只处理 Issue 范围；
- 先复用统一快照、Service、公共组件和既有测试工具；
- 公共字段、单位、接口、实体键和环境需要跨角色确认；
- 不把 fixture 数值写成真实结论；
- 不把完整 CSV、凭证、密钥或大型工件放入仓库；
- 遇到依赖阻塞时记录事实、影响和下游可继续的部分。

## 6. 提交前

```powershell
git status --short
git diff --check
git diff --stat
```

根据改动执行：

```powershell
.\.venv\Scripts\python.exe -m pytest backend\tests data\tests -q
cd frontend
npm run build
```

还要检查：

- 代码、测试与说明文档使用同一术语；
- 实际结果满足验收矩阵；
- 错误路径和空结果已经验证；
- 下游知道怎样运行和验证；
- 没有无关文件、缓存、虚拟环境和敏感数据。

## 7. GitHub 状态

| 状态 | 含义 |
|---|---|
| Open | 问题存在，尚未满足关闭条件 |
| In progress | 负责人正在执行 |
| Review | PR 或交付物正在审查 |
| Blocked | 存在明确外部依赖，已记录影响和解除条件 |
| Done | 交付、证据、文档、下游交接和 Resolution 都已完成 |

PR 合并不自动等于 Issue 完成。任务必须回答原问题，并能由其他成员复查。

## 8. 每日汇报

每人用以下格式汇报：

```text
Issue：
完成内容：
实际结果：
证据位置：
阻塞与风险：
交给谁：
下一步：
```

只报告实际发生的工作。计划、猜测和等待中的事项不写成已完成。

## 9. 立即沟通的情况

- 代码和公共文档对同一字段或状态说法不同；
- 需要改变指标、表、API、端口、环境或模型特征；
- 真实数据结果和 fixture 差异无法解释；
- 发布器可能产生半批数据或跨版本混用；
- 页面重算、排序或改写了正式结果；
- AI 回答没有来源、版本或医疗边界；
- 发现凭证、密钥、完整数据或敏感日志进入提交；
- 验收失败可能影响展示流程。

## 10. 完成定义

任务完成需要同时具备：

- 可运行的交付物；
- 与契约一致的结果；
- 自动化或真实环境证据；
- 必要文档；
- 已合并 PR；
- 明确下游交接；
- Issue Resolution。
