# 医数云策项目组员执行说明 V1.0

> 面向：魏世轩、叶艺鑫、李佳明、胡钰炜及组长王敬博  
> 目的：让每个人随时知道项目现在在哪、自己做什么、依赖谁、交给谁、怎样才算完成。  
> 详细顺序和组长操作见 `组长推进图001.md`；目录、Git、测试规则见 `医数云策小组开发规范方案 V1.0.md`。

## 1. 我们共同交付什么

我们不是分别完成五份独立作业，而是在同一仓库中完成一套能在组长电脑运行、核对、展示和答辩的系统。

当前项目方向是医疗运营和住院出院记录群体分析。数据中的一行代表一次住院出院记录，不等于唯一患者，因此：

- “病例量”表示有效住院出院记录数，不写成患者人数；
- 群体筛选统一称为“住院记录群体分析”；
- 不做个人诊断、治疗建议和跨次住院追踪。

第一轮唯一开发目标是：

> 使用真实 SPARCS 数据完成“疾病病例量 TOP10”的清洗、聚合、服务结果、Flask API、Vue/ECharts 页面和独立核对闭环。

在这个闭环通过前，不同时铺开大量页面、复杂 AI、机器学习、登录和平台化功能。

## 2. 当前处于哪里

截至 2026-08-15，业务代码尚未开始。当前两项任务可以并行：

## 5. 什么时候可以并行

并行不是“各自猜着做”。只有共同接口达到足够状态后才并行：

```text
真实字段已核验
       ↓
TOP10 指标 CONFIRMED
       ↓
服务结果字段 CONFIRMED
       ↓
API 契约 CONFIRMED
       ├─ 魏世轩：实现正式数据任务
       ├─ 叶艺鑫：使用固定服务结果开发 API
       ├─ 李佳明：使用固定 Mock 开发页面
       └─ 胡钰炜：编写验收并核对各层
```

如果契约还是 `DRAFT`，可以讨论和制作原型，但不能把它当作稳定字段向下扩散。进入联调后改为 `FROZEN`，原则上只修错误。

## 6. 每个人收到任务后怎么做

### 6.1 开始前

1. 打开自己的 GitHub Issue；
2. 确认负责人、目标、输入、输出、依赖、目录、截止时间和验收都写清楚；
3. 若依赖未完成，标记被阻塞并立即告诉组长；
4. 从最新 `main` 创建 `feature/<issue-number>-<short-name>` 分支；
5. 只修改当前任务需要的文件。

### 6.2 开发中

- 先用固定样例或 Mock 得到可检查结果，再接真实上游；
- 不私自修改公共字段、指标、表结构、API 或环境版本；
- 公共规则有问题时先更新 Issue，与上下游确认；
- 每完成一个可验证的小结果就 Commit，不积压数天；
- AI 生成代码后必须检查修改文件、输入输出和实际运行结果。

### 6.3 提交前

1. 运行本模块必要验证；
2. 执行 `git status` 和 `git diff --name-only`；
3. 只暂存当前任务相关文件；
4. 更新受影响的公共文档；
5. Push 并创建 PR 到 `main`；
6. 在 PR 中写明验证命令、结果和已知限制；
7. 邀请相关上下游 Review。

详细命令见 `Git仓库开发与提交实操指南.md`。

## 7. GitHub 状态怎样理解

不再单独维护 Markdown 任务板。任务状态直接由 GitHub 表示：

| 实际状态 | GitHub 表示 | 成员应做什么 |
|---|---|---|
| 待领取 | Open、无负责人、无阻塞 | 组长或成员认领 |
| 进行中 | Open、已有负责人 | 持续提交可检查结果 |
| 被阻塞 | 有未关闭依赖，或 Issue 明确记录 Blocked by | 立即说明缺少什么，不静等 |
| 等待 Review | 已创建 PR | 回应 Review，补验证 |
| 完成 | 验收通过、PR 合并、Issue Closed | 下游同步 `main` 并使用 |

## 8. 什么叫完成

“代码写了”“GPT 生成了”“我本地能跑”都不等于完成。

任务只有同时满足以下条件才是 `DONE`：

- Issue 的验收标准已经满足；
- 结果在目标环境真实运行；
- 作者完成本模块验证；
- 公共字段、指标、API 和文档同步；
- 相关上下游完成 Review；
- PR 已合并到 `main`；
- 下游成员能够使用；
- 没有提交密钥、完整数据、缓存、日志和个人绝对路径；
- Issue 或 PR 中有可复查的命令、响应、测试记录或截图。

未完成内容另建 Issue，不使用“基本完成”代替。

## 9. 第一轮各层最低验收

### 数据

- 固定小样本有确定期望结果；
- 清洗与聚合可以重复执行；
- 缺失、重复、文本标准化、排序和并列规则符合文档；
- 有独立 SQL 或脚本核对。

### API

- 正常、合法空结果、非法参数和依赖失败语义明确；
- 字段、类型、单位和排序符合契约；
- 不在 API 中私自重算另一套指标。

### 前端

- 有加载、正常、空数据和错误四种状态；
- 名称、数量、排名和单位与 API 一致；
- 正式版本不使用写死数据冒充接口结果。

### 端到端

- 固定样例在数据结果、API 和页面中一致；
- 组长电脑按 README 能重新启动；
- 代码、文档和测试证据都进入 Git。

## 10. 每天怎样汇报

开工时，每人只需回答：

```text
我今天负责哪个 Issue？
我的输入是什么？
我要交给谁什么结果？
我是否被阻塞？
今天怎样证明完成？
```

收工时，每人只需回答：

```text
完成了什么可运行或可检查结果？
代码或文档在哪个分支 / PR？
实际运行了什么验证？
当前还有什么阻塞？
下一步是什么？
```

所有关键内容更新到 Issue 或 PR，不只在群聊里口头汇报。

## 11. 发现这些情况立即停止并沟通

- 数据、后端、前端对同一字段使用不同名字；
- 每个人算出的 TOP10 不一样；
- 为了等上游，数小时没有任何可推进工作；
- 想新增一个老师没有要求、也不增强闭环的功能；
- 需要修改他人模块或公共契约，却没有通知相关成员；
- PR 包含大量无关重构、格式化或依赖升级；
- `main` 无法运行；
- 完整链路没通，却开始大量开发 AI 或其他页面。

## 12. 全组共同原则

1. 一套公共事实，不在各目录复制指标和接口；
2. 一个当前稳定版本，以 `main` 和组长电脑为准；
3. 一条真实数据链，不使用前端写死数据冒充完成；
4. 一个任务一个 Issue 和短分支；
5. 先确认接口再并行，遇到阻塞立即说；
6. 先做正确、完整、可复现的 TOP10，再扩展其他功能。
