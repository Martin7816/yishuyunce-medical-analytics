# 医数云策项目五人分工与交接说明 V1.0

> 本文件只说明“谁对什么质量负责、第一轮交付什么、怎样交给下游”。项目顺序见 `组长推进图001.md`，开发规则见 `医数云策小组开发规范方案 V1.0.md`。

## 1. 分工原则

1. 主责是质量责任，不是个人独占文件夹；
2. 五个人围绕同一个纵向功能协作，不各自开发互不相连的模块；
3. 每位代码作者测试自己的模块，胡钰炜负责独立核对和端到端验收，不包办全部测试；
4. 公共字段、指标、表、API 和环境由相关上下游共同确认，任何人不能私自改变；
5. 未来可能负责的功能不等于当前任务；当前任务只以 GitHub Issues 为准；
6. AI、分类模型和复杂扩展只有在 M1 通过、老师或范围基线确认需要且时间允许时才开始。

## 2. 五人总览

| 成员 | 长期主责 | 第一轮核心结果 |
|---|---|---|
| 王敬博 | 项目推进、公共契约、Git、集成和部署交付 | 范围与工程基线、Issue 推进、组长电脑可运行版本 |
| 魏世轩 | 数据核验、清洗、聚合、结果发布和指标计算 | TOP10 数据任务、固定样例、服务结果和核对 SQL |
| 叶艺鑫 | Flask、服务结果查询、业务逻辑和接口联调 | TOP10 API、错误语义和接口测试 |
| 李佳明 | Vue、ECharts、页面交互和接口联调 | TOP10 图表及加载、正常、空数据、错误四态 |
| 胡钰炜 | 系统质量、独立核对、端到端验收和后续受控 AI | 验收清单、问题记录、复验和端到端证据 |

## 3. 交接关系

```text
王敬博：范围、环境、公共约定和任务
        ↓
魏世轩：真实字段 → 指标结果 → 服务结果
        ↓
叶艺鑫：服务结果 → Flask API
        ↓
李佳明：API → Vue/ECharts 页面
        ↓
胡钰炜：独立核对整条链，并把问题退回责任模块
        ↓
王敬博：在组长电脑集成、发布和演示
```

这不是严格的“做完一个人才轮到下一个人”。字段、指标、服务结果和 API 契约确认后，可以使用固定样例和 Mock 并行开发。

---

## 4. 王敬博：项目推进与集成

### 4.1 一句话职责

保证五个人按照同一范围和契约工作，并把各模块组合成组长电脑上可运行、可演示、可交付的版本。

### 4.2 当前任务

- 组织五人确认项目概况；
- 固定项目题目、最小技术链路、最低闭环和交付物基线；
- 维护 Wayfinder 地图、Issues、优先级和阻塞关系；
- 主持指标、架构、环境、数据结果和 API 契约确认；
- 建立最小目录、README、配置示例和启动入口；
- Review 公共变更并在组长电脑持续集成；
- 组织 M1 验收、功能冻结、文档和彩排。

### 4.3 需要别人提供

- 魏世轩：真实字段、数据风险、固定结果和运行要求；
- 叶艺鑫：后端依赖、端口、启动命令和接口状态；
- 李佳明：前端依赖、构建命令、接口地址和展示问题；
- 胡钰炜：验收结果、问题严重程度和复验结论。

### 4.4 必须交付

- 已确认的范围和公共决策；
- 明确可执行的 Issues；
- 环境、端口、配置和启动顺序；
- Review 和集成结论；
- 组长电脑可复现版本、Tag、演示与降级方案。

### 4.5 不应包办

- 不替四名成员完成全部业务代码；
- 不在没有证据时替数据负责人决定清洗规则；
- 不单方面修改指标、API 或成员主责；
- 不因为时间紧跳过数据核对、Review 和最终复现。

---

## 5. 魏世轩：数据工程与指标

### 5.1 一句话职责

把真实 CSV 转换为有明确口径、可重复生成、可独立核对并能供后端读取的分析结果。

### 5.2 当前任务

- 核验真实文件、列名、类型、缺失、重复和典型值；
- 找到主诊断描述候选字段并记录风险；
- 制作脱敏固定小样本和预期 TOP10；
- 主写 TOP10 清洗、分组、排序和并列规则；
- 实现正式清洗、聚合和服务结果发布；
- 编写独立 SQL 或脚本核对正式结果；
- 记录执行命令、输入输出、数据量变化和异常。

具体使用 Pandas、Spark、Hive、MySQL 的方式等待最小技术链路确认，不在多个工具中复制不同规则。

### 5.3 需要别人提供

- 王敬博：已确认范围、老师约束和环境边界；
- 叶艺鑫：后端需要读取的服务结果字段；
- 李佳明：页面需要的名称、排名和单位；
- 胡钰炜：固定样例的独立复核和异常反馈。

### 5.4 必须交付

- `docs/01-data-and-feasibility.md`；
- `docs/02-metrics-and-data-contract.md` 的数据与指标部分；
- `data/sample/input` 和 `data/sample/expected`；
- 可重复执行的数据任务、服务结果和核对 SQL；
- 数据任务测试及运行证据。

### 5.5 交接给下游时必须说明

- 结果从哪份输入、按什么规则生成；
- 字段名、类型、单位、是否可空和排序保证；
- 结果如何刷新以及失败时怎样判断；
- 固定样例应该得到什么；
- 哪些数据问题尚未解决。

### 5.6 不应做

- 不把住院记录数解释成患者人数；
- 不在未确认前擅自删除缺失或重复记录；
- 不在 Notebook 中保留唯一正式逻辑；
- 不替后端定义另一套 API，也不替前端制作正式页面；
- 不提交完整原始数据和大型中间结果。

## 6. 叶艺鑫：后端与 API

### 6.1 一句话职责

把已经确认的数据结果通过稳定、有限、可测试的 Flask 接口提供给前端和后续 AI。

### 6.2 当前任务

- 与魏世轩、李佳明确认 TOP10 API 契约；
- 使用固定服务结果先实现 API，不必等待全量数据完成；
- 实现参数校验、正常结果、合法空结果和明确错误语义；
- 使用参数化查询读取正式服务结果；
- 编写代表性 API 测试和请求/响应示例；
- 提供启动、配置、端口和依赖说明；
- 与前端联调，修复实现问题但不私自改变指标。

### 6.3 需要别人提供

- 王敬博：公共环境、端口和架构决定；
- 魏世轩：服务结果字段、类型、样例和刷新方式；
- 李佳明：页面参数、四态和错误展示需求；
- 胡钰炜：契约、边界和端到端问题。

### 6.4 必须交付

- `docs/05-api.md`；
- Flask TOP10 接口和数据访问实现；
- 配置示例、启动方式和健康检查（确实需要时）；
- API 正常、空数据、非法参数和依赖失败测试；
- 与数据结果、前端 Mock 一致的响应。

### 6.5 交接给下游时必须说明

- Method、URL、参数范围和默认值；
- 正常、空数据和错误响应；
- 字段类型、单位和排序保证；
- API 状态是 `DRAFT`、`CONFIRMED` 还是 `FROZEN`；
- 如何启动、调用和判断依赖是否正常。

### 6.6 不应做

- 不在 Route 中复制指标计算或堆放长 SQL；
- 不私自修改数据口径和服务结果字段；
- 不向前端或 AI 返回大量原始住院记录；
- 不用 Mock 掩盖正式服务结果未接通；
- 不提前建设没有调用者的复杂抽象和通用平台。

---

## 7. 李佳明：前端与数据可视化

### 7.1 一句话职责

把后端的真实指标准确转换成用户可以理解、操作并稳定展示的页面，而不是只把页面做得好看。

### 7.2 当前任务

- 根据确认的 API 契约制作固定 Mock；
- 开发 TOP10 页面或图表组件；
- 处理加载、正常、空数据和错误四种状态；
- 正确显示疾病名称、病例量、排名和单位；
- 处理长名称、并列结果、窗口变化和答辩分辨率；
- API 可用后替换 Mock 并联调；
- 提供前端启动、构建、配置和验证说明。

### 7.3 需要别人提供

- 王敬博：前端环境、公共启动方式和展示范围；
- 魏世轩：指标含义、单位和排序规则；
- 叶艺鑫：API 契约、Mock、错误语义和地址；
- 胡钰炜：页面四态和端到端验收问题。

### 7.4 必须交付

- Vue 页面、必要组件和请求封装；
- TOP10 ECharts 图表；
- 加载、正常、空数据和错误四态；
- 前端测试或可复查验证记录；
- 页面截图和真实 API 联调结果。

### 7.5 交接给验收时必须说明

- 页面入口和启动命令；
- 调用了哪个 API、传递了什么参数；
- 四种状态怎样触发；
- 长名称、空结果和错误响应怎样显示；
- 正式版本是否已经关闭或移除临时 Mock。

### 7.6 不应做

- 不直连数据库；
- 不在浏览器里重新计算正式指标；
- 不私自改写 API 字段和单位；
- 不使用写死数据冒充正式接口；
- 不用复杂 3D、动画和大量页面代替数据正确性。

---

## 8. 胡钰炜：系统质量与后续受控 AI

### 8.1 一句话职责

独立证明数据、API 和页面展示的是同一结果，并在条件成熟后把稳定 API 封装为受控 AI 能力。

### 8.2 当前任务

- 独立抽查真实数据文件和固定样例；
- 主写 `docs/06-test-and-acceptance.md`；
- 核对数据任务、服务结果、API 和页面的一致性；
- 验证 API 的正常、空数据、非法参数和依赖失败；
- 验证页面加载、正常、空数据和错误四态；
- 记录问题的复现步骤、预期、实际、责任模块和严重程度；
- 对修复结果执行复验；
- 确认组长电脑能够按说明运行完整链路。

AI 尚未正式进入当前阶段时，不提前开发复杂 Agent。M1 通过后，如果老师或范围基线确认需要，再设计白名单 Tool、模型配置、提示词和固定回归问题。

### 8.3 需要别人提供

- 王敬博：范围、验收边界和组长电脑环境；
- 魏世轩：固定样例、期望结果、核对 SQL；
- 叶艺鑫：API 契约、启动方式和错误语义；
- 李佳明：页面入口、四态触发方式和截图。

### 8.4 必须交付

- 固定样例独立核对结果；
- M1 端到端验收清单和执行证据；
- 问题清单和修复复验记录；
- 组长电脑复现结论；
- 若 AI 进入范围：白名单接口、固定问题和事实一致性验证。

### 8.5 发现问题时必须说明

- 问题发生在哪一层；
- 最小复现步骤；
- 预期结果和实际结果；
- 是否阻塞 M1 或展示；
- 由谁修复；
- 修复后怎样复验。

### 8.6 不应做

- 不替其他成员修复全部问题或编写全部单元测试；
- 不让大模型直接读取完整 CSV 或执行任意 SQL；
- 不允许 AI 输出底层接口未提供的数字或结论；
- 不把 AI 是否“能聊天”当作系统质量；
- 不在核心 API 未稳定时投入大量时间调 Prompt。

## 9. 每次交接的统一格式

上游把结果交给下游时，不要只发一句“我做完了”。至少提供：

```text
关联 Issue / PR：
交付内容：
文件或接口位置：
输入：
输出：
运行 / 调用命令：
实际验证结果：
已知限制：
下游下一步：
```

下游确认能够使用后，上游任务才具备关闭条件。

## 10. 当前与后续的区别

| 阶段 | 五人共同重点 |
|---|---|
| 当前：确定范围 | 执行自主概况；固定最小链路；核验数据 |
| M0 | 固定样例、指标、架构、环境、服务结果和 API 契约 |
| M1 | 五人围绕 TOP10 并行开发、联调和验收 |
| 必要扩展 | 只补课程交付要求或能快速形成完整链路的功能 |
| M4 | 冻结、测试、文档、组长电脑复现和彩排 |

长期主责帮助大家知道以后谁负责，但每天实际任务仍以 GitHub Issue 为准。
